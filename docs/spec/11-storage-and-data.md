# 11 — Storage, caching and safe changes

Rules for how data is stored and changed, across the whole system: SDK API, admin application and
any background work.

## Storage: SurrealDB

- All service data is stored in **SurrealDB**: environments, brands, flags, rules, tokens, users,
  settings, audit events and usage metrics.
- Changes propagate through SurrealDB's **LIVE queries** (`LIVE SELECT`), not by polling the
  database.

## The SDK API serves from a cache

- The Client and Frontend APIs ([04](04-sdk-api.md)) answer from an **in-memory cache** of the
  compiled configuration and the tokens. They do **not** query the database per request.
- Each running instance keeps its cache current with LIVE queries on everything that affects SDK
  responses: flags, flag environments and rules, brand overrides, brands, settings (context-field
  names) and tokens.
- **A change is visible instantly.** When a change is committed, for example a flag is switched off
  or a token is revoked, the next SDK request served after the LIVE notification already reflects
  it. The ETag changes at the same moment. No time-to-live expiry and no polling interval are
  involved.
- On start, and whenever a LIVE subscription is re-established (e.g. after a database restart), an
  instance reloads its cache in full before serving again, so no change is missed.
- The admin application's live behaviour ([05](05-admin-ui.md) G4 and G6) is also driven by LIVE
  queries, either directly or through a service.

## Record ids: no auto-generated ids

An id the database generates on insert is not idempotent: a retried insert creates a second record.
So **every record id is derived from a natural key, or chosen by the caller before the request is
sent.**

| Table | Record id |
|-------|-----------|
| environment | `environment:production` (the key) |
| brand | `brand:⟨bank-a⟩` (the key) |
| flag | `flag:⟨debit-card-payments⟩` (the name) |
| flag environment | `flag_env:['debit-card-payments', 'production']` |
| brand override | `brand_override:['debit-card-payments', 'production', 'bank-c']` |
| settings | `settings:main` |
| api token | `api_token:⟨id⟩`: an id the admin UI generates when the create form opens (e.g. a UUID), reused on retries |
| user | `user:⟨id⟩`: an id generated by the creating client, reused on retries; email stays unique |
| audit event | `audit_event:[⟨operation id⟩, ⟨n⟩]`: the operation that caused it, plus its position within that operation (see below) |
| hourly metrics | `metric_hourly:[flag, environment, appName, hour]` |
| last seen | `flag_last_seen:[flag, environment]` |
| connected app | `client_app:[appName, environment, instanceId]` |
| unknown flag | `unknown_flag:[name, environment, appName]` |

Ids follow SurrealDB's record-id syntax; array ids are used for composite keys. Any table an
implementation adds follows the same rule.

## Every change is idempotent

**Any change can be retried safely.** If a request fails, or its response is lost (for example a
network error after the server already applied it), sending the same request again succeeds and
leaves the same final state as one successful request: no duplicate records and no duplicate audit
events.

How:
- **Operations set target values; they don't apply deltas.** "Switch production ON", not "toggle";
  "set rollout to 25", not "increase by 5"; "add tag `payments`" when it's already there is a
  no-op.
- **Every change carries an operation id**, generated by the client once per user action and
  reused on every retry. Audit events are keyed by it, so a retried change never records a second
  event.
- **Creates use caller-chosen ids** (table above). Creating a record that already exists with the
  same content succeeds and returns it. With different content, the request is rejected as a
  conflict and nothing is overwritten.
- **Deletes, archive, revive, revoke** of something already in the target state succeed.
- **New token secrets** are generated securely by the creating client and sent with the create
  request, so a retry carries the same secret. It is still shown to the admin only once.
- **Exception: SDK traffic.** Unleash SDKs send register and metrics posts without an operation id,
  so a retried post may be counted twice. That is acceptable for usage counts.

## Concurrent edits are merged per field

- Saving writes **only the fields the user changed** (a merge or patch). It never writes back the
  whole record as it was loaded, so values the user didn't touch are never reverted.
- **Two users changing different fields of the same record both keep their changes.** Example: on
  the Settings page one admin changes the CORS origins while another changes metrics retention.
  Both changes stay.
- For flag rules, each part counts as a separate field: the environment switch, the default rule's
  rollout, the default rule's allowlist, and each brand override's rollout and allowlist. Someone
  editing bank-b's override and someone editing bank-c's override in the same environment both
  keep their changes.
- **Only when two users change the same field** does the later save stop and tell the user that the
  field changed since they opened it (who and when). Nothing is silently overwritten; the user
  decides.
- A save that covers several fields (e.g. an environment's rules) is still all-or-nothing
  ([05](05-admin-ui.md)).
